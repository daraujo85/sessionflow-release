# SessionFlow Voice — MVP de conversa em tempo real na aplicação web

## 1. Objetivo

Adicionar à aplicação Angular/PWA do SessionFlow uma experiência de voz com baixa latência, capaz de:

- ouvir o usuário pelo microfone do navegador;
- transcrever a fala;
- executar ações globais do SessionFlow ou enviar texto para uma sessão;
- receber a resposta de forma incremental;
- começar a sintetizar a resposta antes de ela terminar por completo;
- reproduzir a resposta em áudio usando **Piper**;
- evitar, no MVP, que o assistente reconheça a própria voz como se fosse o usuário.

O objetivo não é construir um “Gemini dentro do SessionFlow”. O objetivo é criar um **canal de voz rápido para as capacidades que o SessionFlow já possui**.

---

## 2. Decisão principal de transporte

### Browser ↔ Backend: WebSocket

Usar **WebSocket seguro (`wss://`)** entre Angular e o backend.

Não usar gRPC diretamente no navegador para o hot path.

Motivos:

- WebSocket é nativamente suportado pelo browser;
- é full-duplex;
- aceita mensagens JSON e frames binários;
- é suficiente para áudio PCM em tempo real;
- simplifica cancelamento, streaming de transcript, streaming de texto e streaming de áudio no mesmo canal;
- evita adicionar gRPC-Web/WebTransport antes de existir necessidade real.

### Backend ↔ STT/TTS locais

Dentro da máquina/servidor:

- WebSocket termina no `voice-gateway`;
- `voice-gateway` conversa com STT e TTS por **gRPC local**, Unix Socket ou chamada direta em processo;
- se STT/TTS estiverem em containers separados, preferir gRPC no Docker network;
- **RabbitMQ, MongoDB e SSE não entram no caminho de cada chunk de áudio**.

RabbitMQ pode continuar existindo para eventos normais do SessionFlow, mas não deve transportar PCM ou cada delta de voz.

## 4. Regra de ouro do hot path

O caminho crítico deve ser:

```text
microfone
→ WebSocket
→ VAD/STT
→ roteamento
→ SessionFlow/agente
→ texto incremental
→ Piper
→ WebSocket
→ alto-falante
```

Evitar no hot path:

```text
microfone
→ upload de arquivo completo
→ banco
→ RabbitMQ
→ job
→ transcrição
→ resposta completa
→ TTS completo
→ download do WAV
```

Esse segundo fluxo funciona, mas produz a sensação de “gravei uma mensagem de áudio e esperei uma resposta”, não de conversa.

## 5. Frontend Angular

Criar, no mínimo:

```text
src/app/core/voice/
├── voice.service.ts
├── voice-socket.service.ts
├── microphone.service.ts
├── audio-playback.service.ts
├── voice-state.ts
└── worklets/
    ├── capture.worklet.js
    └── playback.worklet.js
```

### 5.1 Captura do microfone

Usar:

```ts
navigator.mediaDevices.getUserMedia({
  audio: {
    echoCancellation: true,
    noiseSuppression: true,
    autoGainControl: true,
    channelCount: 1
  }
});
```

Não depender de `sampleRate` solicitado no `getUserMedia`, porque o navegador/dispositivo pode ignorá-lo.

O `AudioWorklet` deve:

1. receber o áudio nativo do browser, normalmente Float32;
2. converter para mono;
3. resamplear para **16 kHz**;
4. converter para **PCM signed 16-bit little-endian**;
5. mandar frames pequenos pelo WebSocket.

Sugestão:

```text
sample rate: 16000 Hz
channels:    1
format:      PCM s16le
frame:       20 ms
bytes/frame: 640 bytes
```

Isso gera aproximadamente 32 KB/s enquanto o microfone estiver enviando áudio.

### 5.2 Não usar MediaRecorder como caminho principal

`MediaRecorder` continua útil para gravação tradicional.

Para o modo conversacional, preferir `AudioWorklet`, porque evita:

- blobs maiores;
- espera por fechamento de chunk;
- decode de WebM/Opus no backend;
- latência desnecessária.

## 7. Máquina de estados mínima

```text
IDLE
  ↓
LISTENING
  ↓
ENDPOINTING
  ↓
TRANSCRIBING
  ↓
ROUTING
  ↓
WAITING_AGENT
  ↓
SPEAKING
  ↓
COOLDOWN
  ↓
LISTENING
```

Estados adicionais:

```text
DISCONNECTED
CANCELLED
ERROR
```

O frontend e o backend devem conhecer o `turnId` atual.

Nenhum áudio ou texto de uma resposta velha pode continuar tocando depois que o turno tiver sido cancelado.

---

## 8. VAD e detecção de fim de fala

Não esperar o usuário clicar em “parar gravação”.

O backend deve manter um buffer contínuo e detectar:

```text
fala começou
fala continua
silêncio
fim do utterance
```

Para o MVP:

- VAD WebRTC ou Silero VAD;
- silêncio de aproximadamente **350–600 ms** pode encerrar uma frase;
- tornar esse valor configurável.

Não usar um timeout muito alto, senão o sistema parece lento.

Não usar um timeout muito baixo, senão pausas naturais quebram a frase.

---

## 9. STT

### MVP recomendado

Usar o `faster-whisper` já carregado em um processo persistente.

Não criar um novo processo/modelo para cada fala.

```text
stt-worker
  inicia
  ↓
carrega modelo
  ↓
fica quente
  ↓
recebe streams/utterances
```

Preferir inicialmente um modelo rápido o suficiente para a máquina disponível.

O STT deve receber áudio enquanto o usuário fala, mesmo que a transcrição final só seja consolidada no fim do utterance.

Idealmente emitir:

```text
transcript.partial
transcript.partial
transcript.final
```

O `final` é o único texto que dispara uma ação no SessionFlow.

### Regra

Nunca executar ferramentas ou enviar comando ao agente baseado apenas em transcript parcial.

---

## 10. Roteamento dentro do SessionFlow

Preservar as quatro capabilities já desenhadas:

```text
listActiveSessions
getSessionStatus
listSessionTasks
sendSessionInput
```

### Consultas rápidas

Perguntas como:

```text
"quais sessões estão ativas?"
"o que aconteceu na sessão pagamentos?"
"qual é o próximo passo da sessão X?"
```

devem usar o estado/snapshot do SessionFlow diretamente sempre que possível.

Não mandar tudo para um LLM só para descobrir algo que o backend já sabe.

### Conversa com uma sessão

Exemplo:

```text
"na sessão pagamentos, verifica por que o teste está falhando"
```

Fluxo:

```text
STT final
→ resolve sessionId
→ sendSessionInput(sessionId, text)
→ fluxo normal da sessão
→ worker/agente
→ saída incremental
```

Não criar um segundo caminho de injeção no tmux.

Reutilizar o mesmo serviço/porta usado pela UI normal.

---

## 11. Streaming da resposta do agente

Este ponto é obrigatório para a sensação de velocidade.

Se o voice-gateway só receber a resposta quando o agente terminar tudo, a latência continuará ruim mesmo usando Piper.

O Worker deve produzir algo equivalente a:

```text
session.response.start
session.response.delta
session.response.delta
session.response.delta
session.response.end
```

Exemplo:

```json
{
  "type": "session.response.delta",
  "sessionId": "session-123",
  "turnId": "uuid",
  "text": "Encontrei o problema."
}
```

O voice-gateway vai acumulando esses deltas para TTS.

---

## 12. TTS com Piper

Para o modo conversacional, usar **Piper** como engine padrão.

Requisitos:

- processo persistente;
- voz carregada uma vez;
- nenhuma inicialização de modelo por frase;
- síntese por segmentos curtos;
- saída PCM enviada imediatamente ao browser.

### Não esperar a resposta inteira

O texto do agente pode chegar assim:

```text
"Encontrei o problema."
" O teste está falhando porque..."
" A correção é..."
```

Assim que existir um trecho estável, ele entra na fila do Piper.

Regra inicial de chunk:

```text
final de frase (. ! ? :)
OU
buffer >= ~100 caracteres
OU
~350 ms sem novo texto e já existe conteúdo falável
```

Evitar mandar para o Piper:

- markdown;
- blocos de código;
- URLs gigantes;
- stack traces;
- tabelas;
- símbolos desnecessários.

Reutilizar/centralizar um `speech_formatter`:

```text
display_text → texto completo para tela
speech_text  → texto curto e natural para TTS
```

---

## 13. Playback no navegador

Não usar um `<audio>` novo para cada frase.

Criar uma fila contínua:

```text
PCM chunk
PCM chunk
PCM chunk
...
```

O `AudioWorklet` de playback mantém um pequeno jitter buffer.

Objetivo inicial:

```text
buffer antes de começar: 80–150 ms
```

Não deixar acumular vários segundos de áudio.

Se o usuário cancelar o turno:

```text
limpar fila imediatamente
parar TTS pendente
invalidar turnId
```

---

## 14. O problema do assistente ouvir a própria voz

Para o MVP, implementar **half-duplex controlado**.

### Enquanto o Piper estiver falando

Frontend:

```text
SPEAKING = true
```

Durante `SPEAKING`:

- manter `echoCancellation: true`;
- parar de enviar frames do microfone **ou** marcar os frames para o servidor ignorá-los;
- não executar VAD/STT do usuário;
- ao terminar o áudio, aguardar um pequeno tail de eco.

Sugestão inicial:

```text
TTS termina
→ 250–400 ms de COOLDOWN
→ reabre LISTENING
```

Isso resolve a classe principal do problema:

```text
assistente fala
→ alto-falante entra no microfone
→ STT transcreve a própria resposta
→ assistente responde a si mesmo
```

### Consequência

No MVP o usuário não consegue interromper o assistente no meio da fala.

Isso é intencional.

**Barge-in/full-duplex fica para a segunda etapa.**

---

## 15. Barge-in — depois do MVP

Somente depois do fluxo básico estar estável.

Para permitir:

```text
assistente está falando
+
usuário começa a falar
→ TTS para imediatamente
→ fala do usuário vira novo turno
```

será necessário combinar:

- AEC real;
- VAD durante playback;
- cancelamento instantâneo da fila TTS;
- identificação de fala humana acima do resíduo de eco;
- controle rigoroso de `turnId`;
- possivelmente WebRTC Audio Processing/AEC3.

Não colocar isso como blocker do primeiro MVP.

```yaml

  stt:
    # faster-whisper
```

Fluxo interno:

```text

  ↓ WSS

  ├── gRPC → stt
```

## 18. Backpressure

Toda fila precisa ter limite.

### Microfone

Se o servidor não conseguir consumir:

- não acumular áudio indefinidamente;
- fechar a conexão em caso de atraso extremo;
- registrar `audio_backpressure`.

### Agent output

Não acumular centenas de deltas esperando TTS.

Agrupar texto em frases.

### TTS

Fila inicial:

```text
máximo: 2 ou 3 segmentos prontos à frente
```

Se um novo turno cancelar o atual:

```text
descartar todos os segmentos antigos
```

---

## 19. Cancelamento

Cada interação recebe:

```text
conversationId
turnId
sessionId opcional
```

Regra:

```text
novo turnId
→ tudo do turnId anterior pode ser cancelado
```

O cancelamento precisa chegar a:

- transcrição pendente;
- request no agente quando possível;
- fila de chunks de texto;
- Piper;
- playback do browser.

---

## 20. Autenticação do WebSocket

Não colocar o JWT longo na URL.

Fluxo simples:

```text
Angular autenticado
→ POST /api/voice/ticket
→ backend cria ticket aleatório de uso único, TTL curto
→ Angular abre wss://.../ws/voice?ticket=...
→ gateway consome/invalida ticket
```

Sugestão:

```text
TTL: 30–60 segundos
single use: true
```

Depois do handshake, a conexão autenticada permanece vinculada ao usuário.

---

## 21. Keepalive e reconexão

Implementar:

```text
ping/pong: 15–30 s
timeout:   45–60 s
```

Se desconectar:

```text
parar captura
parar playback
cancelar turn atual
reconectar
criar nova conversation transport
```

Não tentar continuar áudio antigo após reconexão.

## 23. Meta inicial de percepção

Não tratar estes números como SLA; usar como alvo de profiling.

Para consultas simples do SessionFlow:

```text
fim da fala → transcript final:       ~0.3–0.8 s
transcript → resposta de backend:     ~0.05–0.3 s
texto → primeiro áudio Piper:         ~0.1–0.4 s
```

Para pergunta enviada a um agente:

```text
fim da fala → transcript final
+ tempo até primeiro delta do agente
+ primeiro segmento Piper
```

O maior custo provavelmente será o **tempo até o primeiro texto útil do agente**, não WebSocket.

## 25. Modos de conversa

### Global

```text
mode = global
```

Usado para:

- listar sessões;
- consultar status;
- listar tarefas;
- selecionar/vincular sessão;
- comandos gerais.

### Sessão vinculada

```text
mode = session
sessionId = ...
```

Tudo que o usuário fala é enviado para aquela sessão, salvo comandos locais como:

```text
"voltar para o modo global"
"parar"
"cancelar"
```

Isso reduz bastante a ambiguidade de roteamento.

## 26. Limitações da PWA que devem ser aceitas no MVP

Esta solução funciona bem **com a PWA aberta/ativa**.

Não assumir no MVP que o navegador conseguirá manter uma experiência de assistente permanente quando:

- a tela estiver bloqueada;
- o Android suspender a aba/PWA;
- o app estiver longamente em background;
- o sistema revogar/suspender o microfone.

Se no futuro o requisito for:

```text
"Hey SessionFlow" com a tela apagada e app em background
```

isso volta a exigir uma camada Android nativa.

Não misturar esse problema com o MVP atual.

## 27. O que NÃO fazer no primeiro MVP

Não implementar agora:

- wake word;
- full-duplex;
- barge-in;
- WebRTC peer-to-peer;
- WebTransport;
- Kafka;
- áudio em RabbitMQ;
- persistência de cada frame PCM;
- gravação permanente do microfone;
- clone de voz;
- lip sync/avatar;
- troca dinâmica entre vários TTS;
- detecção emocional;
- múltiplos STTs concorrentes;
- resumo por LLM para perguntas que o snapshot já responde.

Primeiro fazer uma conversa rápida e estável.

## 29. Critério de pronto do MVP

O MVP está pronto quando for possível abrir a PWA no celular e executar:

```text
Usuário:
"Quais sessões estão ativas?"

SessionFlow:
"Existem três sessões ativas: pagamentos, dashboard e testes."
```

e depois:

```text
Usuário:
"Na sessão pagamentos, qual foi o último progresso?"

SessionFlow:
"O último progresso foi a correção do listener..."
```

e:

```text
Usuário:
"Envia para ela verificar os testes que estão falhando."

SessionFlow:
"Vou verificar."

[texto entra na sessão]

SessionFlow:
"Encontrei dois testes falhando..."
```

sem:

- upload de WAV completo;
- esperar a resposta inteira para iniciar o TTS;
- RabbitMQ no caminho de áudio;
- o assistente responder à própria voz.

## 30. Decisão resumida

Para este MVP:

```text
Angular/PWA
  └─ AudioWorklet + WebSocket

Backend Docker
  └─ voice-gateway

STT
  └─ faster-whisper quente/persistente

TTS
  └─ Piper quente/persistente

SessionFlow
  └─ capacidades existentes
  └─ mesmo caminho de sendSessionInput
  └─ output incremental do agente

Turn-taking
  └─ half-duplex no MVP
  └─ echoCancellation do browser
  └─ mic ignorado durante TTS
  └─ cooldown curto

Streaming
  └─ PCM binário no WebSocket
  └─ transcript parcial/final
  └─ agent text delta
  └─ TTS por frase, sem esperar resposta completa
```

A principal otimização não é trocar HTTP por uma tecnologia “mais rápida” isoladamente.

A principal otimização é **não trabalhar mais em bateladas**.

O sistema precisa começar a transportar, processar e responder enquanto a interação ainda está acontecendo.
